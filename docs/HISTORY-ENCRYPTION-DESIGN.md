# 历史加密设计

现状：历史全部明文存在 `~/Library/Application Support/Cubby`（`history.json` + `Images/` 下的图片、富文本格式、缩略图、译图，另有 `security-log.json` 与迁移 / 损坏备份）。目录 `0700`、文件 `0600` 只挡得住**其他用户账户**；同一用户下任何未沙盒化的应用、脚本、依赖安装脚本都能静默读取，没有任何系统提示。FileVault 只防丢机 / 拆盘，登录后对所有进程透明。
目标：其他应用读到的只有密文；要拿到密钥必须经过钥匙串，系统会弹窗问用户。
原型：`docs/prototypes/history-encryption.html`（2026-10-13 用户确认，「按推荐来」：始终开启、预览打开时临时解密并在退出时删除、密钥丢失时从空历史开始并保留旧数据、接受降级期间的删除在升级后复现）。已经过一轮魔鬼代言人审查，修订点见第 8 节。

## 1. 威胁模型

| 能防 | 不能防 |
| --- | --- |
| 同一用户下的其他应用 / 脚本**静默**批量读取数据目录（钥匙串条目只信任 Cubby 的签名；Cubby 启用了 Hardened Runtime，其他进程无法读它的内存或注入代码） | 已获得管理员 / root 权限，或已骗到你登录密码的恶意软件（可离线解开整个登录钥匙串） |
| 把数据目录打包、同步到网盘、误传给别人 | 在你复制的当下读取系统剪贴板的应用（系统剪贴板本身，与 Cubby 无关） |
| 通过文件名（内容哈希）比对确认「你是否复制过某张图」 | 被授予「辅助功能」或「屏幕录制」、能操控或看到 Cubby 窗口的应用 |
| | 你主动拖出 / 用其他应用打开的副本（见 E9，同一用户的进程可见） |
| | 用旧的加密文件回滚历史（只保证机密性与完整性，不保证新鲜度） |
| | 在钥匙串询问中被你点了「允许」的应用（见 E8 的弹窗说明） |

## 2. 决策

| # | 决策 |
| --- | --- |
| E1 | **范围**：数据目录里一切由剪贴板内容派生的数据都加密——历史（文本、OCR 文字、翻译、链接标题、内容哈希）、图片原图、富文本格式、缩略图、译图、地址守护日志、迁移备份、损坏备份。不加密：偏好设置 plist（不含内容）、用户主动保存到桌面等位置的截图（用户自己的文件）、翻译 API Key（本来就在钥匙串） |
| E2 | **始终开启，不提供开关**（推荐，见第 7 节问题 1）。新安装直接加密；老用户升级后首次启动自动迁移 |
| E3 | **密钥**：256 位随机主密钥，存入登录钥匙串（通用密码，service `<bundleID>.history`）。account：默认数据目录固定为 `default`；`CUBBY_DATA_DIR` 指定的目录在 `Vault/vault-id` 存一个随机 UUID（明文，不敏感），account 为 `vault-<UUID>`——**不由路径派生**，改用户名、换 Mac、路径写法不同都不影响。访问控制靠钥匙串 ACL（只信任创建它的应用的签名）；旧式文件钥匙串**不强制** `ThisDeviceOnly` 等可访问性属性，不以它们为安全前提。进程内只读取一次并缓存。用 HKDF-SHA256 派生加密密钥、文件名密钥与密钥 ID |
| E3a | **密钥只增不改**：生成只走 `SecItemAdd`；遇到 `errSecDuplicateItem`（另一实例刚生成）就重新读取；任何路径都不对主密钥 `SecItemUpdate` 或删除。只有「`errSecItemNotFound` **且** `Vault/` 不存在」才允许生成新密钥；`errSecUserCanceled`、`errSecAuthFailed`、`errSecInteractionNotAllowed` 等一律按「已锁定」处理（E8 ①）。首次生成、迁移、合并都在 `Vault/.lock` 上持 `flock`，同一数据目录同时只有一个实例做这些事 |
| E3b | **开发与测试**：仅 `#if DEBUG` 编译的密钥来源（环境变量指向测试密钥文件，或内存密钥），E2E 与 CI 不碰钥匙串、不弹窗；Release 构建中不存在这条路径（否则就是后门），用单元测试 + 构建检查守住 |
| E4 | **文件格式**：自有头部（魔数 `CBYV`、格式版本、密钥 ID）+ AES-256-GCM（CryptoKit，硬件加速）。历史与日志按 64 KB 分段、STREAM 构造（随机前缀 + 段序号 + 末段标记作 nonce），检测篡改、截断、段重排；图片等单段加密。AAD 包含头部与文件角色 / 名称，防止把一个文件换成另一个。密钥 ID 不符报「密钥不对」，与「内容损坏」严格区分 |
| E5 | **目录布局**：新建 `<数据目录>/Vault/`——`history.cubby`、`security-log.cubby`、`Blobs/<名称>`、`Backups/`、`vault-id`（仅自定义目录）、`.lock`。图片文件名改为 `HMAC-SHA256(文件名密钥, 种类 + 内容哈希)`，保持去重、符合现有文件名字符集，不再暴露明文哈希与扩展名。放进新目录是为了**降级安全**：旧版本只清理 `Images/` 里不认识的文件，碰不到 `Vault/` |
| E6 | **升级迁移（顺序固定，可中断续做）**：持锁 → ① 逐个把被引用的图片加密写入 `Vault/Blobs/`（已存在则跳过）→ ② 写 `history.cubby`、fsync、**读回校验** → ③ 把 `history.json`、`Images/`、`history.v*.bak.json` 原子改名进 `.migrated-plain/`，损坏备份加密后移入 `Vault/Backups/` → ④ 递归删除 `.migrated-plain/`。每次启动先删掉残留的 `.migrated-plain/`；②之前崩溃则明文完好、下次重做。面板此时显示「正在加密历史…」占位 |
| E7 | **降级**：旧版本看不到 `history.json`，显示空历史并开始写新的明文历史。再次升级时把这部分明文条目合并进加密历史后删除明文：按内容哈希去重；同一内容取较新的时间、收藏取并集、译文以加密历史为准；合并后按时间排序并应用条数上限。**降级期间的删除 / 清空不会作用到加密历史**，升级回来后那些条目会重新出现——发布说明与使用说明写明 |
| E8 | **钥匙串与解密异常（任何情况下都不自动删除加密数据）**：① **已锁定**（用户在询问中拒绝、钥匙串被锁、其他读取错误）：本次运行只在内存中记录；所有写入方都不写盘——历史保存、图片写入、安全日志、文字识别回写、缩略图回填、译文 / 译图、图片清理；面板与设置显示提示与「重试」。重试成功后：先把内存中的新条目合并进解密出的历史 → 再开启写盘 → 最后才允许图片清理。② **密钥找不到但 `Vault/` 存在**：`Vault/` 改名为 `Vault-unreadable-<日期>/` 保留，从空历史重新开始，设置里说明并提供「在访达中显示」；之后每次启动检查这些目录的密钥 ID，若钥匙串恢复了对应密钥就自动还原。③ **`Vault/` 不存在但密钥存在**（时间机器恢复、迁移助理——数据目录排除在备份之外）：静默用现有密钥建新 `Vault/`。④ **密钥正确但内容损坏**：历史文件加密移入 `Backups/`，**本次运行不做图片清理**（图片留给备份）；只有成功读取历史之后才清理孤儿图片 |
| E9 | **交给其他应用的文件**：拖到访达等支持「文件承诺」的目标用 `NSFilePromiseProvider`，由目标自己写文件，不落临时盘；必须给出文件路径时（「用预览打开」、只接受 URL 的拖放目标），解密到 `$TMPDIR/Cubby-Shared/<随机子目录>/<可读文件名>`，退出时与下次启动时删除（不按时间删，避免「预览」里正在编辑的文件被删）。第 1 节如实写明：这类副本同一用户的进程可见 |
| E10 | **应用内读取**：删除返回文件 URL 的接口（`imageURL(for:)`、`BlobStore.url(for:)`），让编译器找出全部约 15 处调用点逐个改为读解密后的数据：卡片 / 预览 / 网格 / 晾衣绳 / 翻译卡显示、晾衣绳编辑、贴到屏幕、粘贴、文字识别、图片翻译、缩略图（`CGImageSourceCreateWithData`、Vision 的数据入口） |
| E11 | **明文残留**：删除只是取消链接，固态盘上无法保证覆写；迁移完成后旧明文所在的块由系统回收。说明里继续建议开启 FileVault（数据目录已排除在时间机器之外） |
| E12 | **性能预算**：加载时把历史解密到 `vm_allocate` 的匿名内存，解码后立即归还（项目实测 malloc 大块释放后仍滞留在进程里，不能用普通 `Data`）；验收按**实测**：26 MB 历史加载的常驻内存增量 < 2 MB、解密耗时 < 30 ms；单张图片解密 < 1 ms/MB；迁移 400 个文件 / 65 MB 预计 1–2 秒 |
| E13 | **文档与界面**：设置 › 历史新增「加密」一行；PRIVACY.md、README、使用说明把「不额外加密」改为新说明，写清第 1 节的能防 / 不能防，以及钥匙串询问该怎么选 |

## 3. 钥匙串询问怎么选（写进使用说明与设置页说明）

- 询问里的应用名可以伪造。**只有刚安装或更新了 Cubby、而且是 Cubby 自己在问时才允许**；其他任何时候、任何应用来问，一律「拒绝」。
- 拒绝不会丢数据：Cubby 进入「已锁定」，新复制的内容暂存在内存中，点「重试」并允许后合并回历史。
- 正式版之间签名稳定，正常升级不会出现询问；只有装过本地构建版等签名不同的版本时才会问一次。

## 5. 实现

| 层 | 内容 |
| --- | --- |
| CubbyCore | `EncryptedFileFormat`（头部、分段 STREAM 加解密，纯函数）；`HistoryKeys`（HKDF 派生、密钥 ID、文件名 HMAC）；`HistoryKeyProviding` 协议（读取 / 只增生成，区分「不存在」与「锁定」；测试用内存实现）；`EncryptedHistoryStorage`（实现现有 `HistoryPersisting`，复用 `StreamingFileWriter` 的原子替换与 `HistoryMigrator` 的版本链）；`EncryptedBlobStore`（只提供数据接口）；`PlaintextMigration`（E6 / E7）；`VaultLock`（flock）；`SecurityLogStore` 改用加密文件，锁定时不写；`ClipStore` 的持久化开关改为可在运行中切换的状态（E8 ① 的重试合并） |
| 应用 | `KeychainHistoryKeyProvider`（E3 / E3a）；`AppPaths` 新增 `Vault`；拖出改用文件承诺 + `SharedFileExporter`（E9）；E10 的调用点改造；设置 › 历史的加密行；`PanelWarning` 新增「历史已锁定」 |
| 测试 | 格式：往返、篡改任一字节、截断、段重排、换文件、错误密钥、密钥 ID 不符；密钥：并发首次生成不覆盖（重复项 → 重读）、各类错误码 → 锁定；迁移：每一步之后崩溃再启动都能续做且不丢数据、校验失败不删明文、降级明文合并规则；E8 ①–④ 各一组（重点：锁定 / 损坏时图片一个都不删、重试后先合并再写）；E9 导出目录与清理；Release 构建不含测试密钥来源；CubbyCore 覆盖率保持 ≥ 95% |
| E2E | `make e2e-panel` 用 `CUBBY_DATA_DIR` + 测试 bundle ID + DEBUG 测试密钥：迁移占位、拖出得到可读文件、锁定横幅；检查数据目录下不再有可被直接解析的 PNG / JSON |

## 6. 备选方案（为什么不选）

| 方案 | 结论 |
| --- | --- |
| 数据保护钥匙串（嵌入 Developer ID 描述文件 + `keychain-access-groups`） | 访问按团队访问组强制，签名变化不弹窗、没有可被社工的「始终允许」，比旧式钥匙串更好。但需要管理描述文件，权利配置错误时系统直接拒绝启动应用；Developer ID 描述文件是否支持该权利需实测。**实现第一步先花半天做验证**：可行就改用它（E3 只换密钥存放处，其余不变），不可行按本文的旧式钥匙串 |
| ↳ 验证结果（2026-10-13） | Developer ID 签名、无描述文件的程序访问数据保护钥匙串返回 `-34018`（缺少权利）；本机没有 macOS 的 Developer ID 描述文件，且强制描述文件会让从源码构建的贡献者无法运行。**采用旧式登录钥匙串**；密钥存放藏在 `HistoryKeyProviding` 之后，日后改用数据保护钥匙串只需替换这一个类型 |
| 应用沙盒 + macOS 14「应用数据」保护 | 模拟粘贴、任意文件访问、输入监控都要重做，对剪贴板管理器侵入太大 |
| 只加密 `history.json` | 截图与图片仍是明文，而它们恰恰最敏感 |

## 7. 待确认

1. **始终开启，还是提供开关？** 推荐始终开启：开关只给「想让别的工具读历史」的极少数人用，却会多一条未加密路径要维护和测试。
2. **「用预览打开」等必须给出文件时临时解密、退出时删除**，是否可以接受？（拖到访达改用文件承诺，不落临时盘。）
3. **密钥丢失时从空历史重新开始、旧数据改名保留（钥匙串恢复后自动还原）**，不做恢复密钥，是否可以接受？
4. **降级期间删除的条目，升级回来会重新出现**，是否可以接受？（要避免就得让旧版本也懂加密格式，做不到。）

## 8. 审查修订记录（2026-10-13 魔鬼代言人）

- C1：密钥生成改为只增不改 + 进程锁（E3a），避免并发实例覆盖主密钥导致历史永久不可解。
- H1：account 不再由路径派生（E3），避免「密钥还在却被判为丢失」；新增自动还原（E8 ②）。
- H2：威胁模型改写——可访问性属性在旧式钥匙串上不生效、加入「骗到登录密码的恶意软件」与回滚、去掉「防聚焦索引」的说法；不再教用户「点始终允许」（第 3 节）。
- H3：锁定 / 损坏状态下全部写入方静默、重试先合并再写、损坏时不清理图片（E8）。
- H4：拖出改用文件承诺；临时文件改为退出时删除；如实说明可见性（E9）。
- H5：迁移提交顺序写死、合并规则与「降级期间删除会复活」写明（E6 / E7）。
- H6：DEBUG 专用测试密钥来源，Release 不含（E3b）。
- M1–M5：内存预算改为匿名内存 + 实测验收（E12）；E10 改为删除 URL 接口、列出调用点；补充数据保护钥匙串备选与验证步骤（第 6 节）；回滚不在目标内（第 1 节）；时间机器 / 迁移助理的处理（E8 ③）。
